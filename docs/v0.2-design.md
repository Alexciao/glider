# Glider v0.2 design (whole-library EGL replacement)

Source of truth for the Phase 1 refactor and the Phase 2 feature work. Inputs: `docs/audit-v0.1.md`,
`docs/research/legendary-v0.2.md` (cited below as **L§n**), `docs/research/heroic-v0.2.md`,
`docs/research/store-webview.md`, `docs/download-perf.md`. The contract itself is
`src/Glider.Core/Contracts/Models.cs` + `IGliderRpc.cs`; this doc explains the parts code can't.

## 1. Wire protocol

- `state` event = small `AppSnapshot` (app, auth, connectivity, library *status*, queue, sessions, storage, EGL,
  overlay, collections, settings, onboarding). Coalesced like v0.1 (33 ms trailing). Must stay a few KB: never
  put per-game lists in it except the queue (≤ unfinished + 20 finished jobs) and EGL installs.
- `library` event = `LibraryDelta {revision, reset, upserts, removes}`. Core keeps one immutable
  `ImmutableDictionary<string, GameSummary>` + revision; any change to any game produces one delta with just
  the changed summaries (coalesced per 50 ms). UI: `library.get` once at boot (reset), then apply deltas; on a
  revision gap call `library.get` again. `GameSummary` is the only per-game shape the grid needs.
- `progress` event = `JobProgress` (≤10 Hz for the running job). Phase groups are null when they don't apply
  (see §5). Graph samples: Core keeps ≈1 Hz `JobSample`s per job (ring, downsampled to ≤600 points) for
  `jobs.getHistory`, so graphs survive a UI reload.
- `navigate` (route string) from tray / protocol links / toasts; `store` = native Store view state.
- Every per-game RPC takes `AppName`. `GliderError.AppName` and `Notice.AppName/JobId` let the UI de-duplicate.

## 2. Game model (Core)

`GameCatalog` (pure, tested) builds `GameSummary`/`GameDetail` from **files read directly** (L§2.5): Legendary's
`metadata/<app>.json`, `assets.json`, `installed.json`, `entitlements.json`, plus Glider's own `state/games.json`.
Parse with retry (3× / 100 ms, files are rewritten in place), treat missing/corrupt as unknown (never "not
installed"). Field mapping is L§2.3: kind from `mainGameItem` / `addons/launchable` category, hidden content DLC
(category `hidden`) and `mods` are excluded, cloud saves = `CloudSaveFolder`, offline = `CanRunOffline` (default
true), third party = `ThirdPartyManagedApp|ThirdPartyManagedProvider` (+ `partnerLinkType`), folder =
`FolderName`, added = entitlement `grantDate` else `creationDate`, art = `DieselGameBoxTall` (tile) /
`DieselGameBox` (hero), falling back to each other then to a generated placeholder.

- Cold start: Core writes `cache/library.json` (the last `GameSummary` list) after each change (debounced) and
  serves `library.get` from it before Legendary's files are even parsed; the file-based rebuild then emits a
  delta. Target: interactive library with 500 games < 1.5 s.
- Background sync (`library.refresh`, at startup after auth warm-up, every 30 min, after the Store tab is left
  following checkout activity): `legendary list -T --json` on the **metadata lane**; then rebuild from files and
  diff. Update check = compare `assets.json` vs `installed.json` (L§10), refreshed by one
  `list-installed --check-updates` (metadata lane). The UI never waits on any of this.
- Update download size: lazily per game (dry run, metadata lane), only for installed games with an update.

### 2.1 Profiles / quirks
`GameProfiles` = a small table keyed by AppName (plus heuristics) giving optional quirks. Generic code reads
quirks; nothing else may branch on a specific game:
- `TrackedProcessNames` (stub launchers that re-parent, e.g. Fortnite: `FortniteLauncher`, `FortniteBootstrapper`,
  `FortniteClient-Win64-Shipping(_EAC|_EAC_EOS|_BE)?`), `LivenessExe`, `LooksLikeInstall` probe,
- `AntiCheat` + setup (EAC: `EasyAntiCheat_EOS_Setup.exe` path + product id; generic EAC detection = an
  `EasyAntiCheat` folder with `Settings.json` in the install; BattlEye = `BattlEye` folder),
- `InstallComponentsSource` (SDL from api.legendary.gl for the titles that have it, else raw tags from manifest),
- `QuickScanFolders` for the drive quick scan, version ordering (`++Fortnite+Release-x.y-CL-n` CL ordering is the
  generic "CL if present else component compare" rule).
Fortnite is entry #1; it must keep every v0.1 behaviour.

### 2.2 Process tracking
Per session: Glider spawns the exe from `launch --json` (v0.1 rule), then tracks the spawned PID **and its
descendants** (Toolhelp snapshot every 1.5 s while the session lives; no polling when nothing runs) plus the
profile's tracked names (re-parented stubs). Session ends when nothing tracked remains for 5 s. Third-party
launches are `Untracked`. Playtime accumulates per game (flush every 30 s + on exit) into `games.json`.

## 3. Lanes (job runner) — L§1.8, binding

| Lane | Concurrency | What |
|---|---|---|
| **W** writer | 1 job at a time, user-ordered queue | install/update/repair/verify(+repair)/modify/move/uninstall/import, overlay install/update/remove, first-time save-path setup |
| **M** metadata | 1 at a time | `list -T --json`, `list-installed --check-updates`, `info`, `status`, `activate`, `list-saves`, update dry runs. Never start while a W job is in its pre-download phase (spawn → first progress line) |
| **S** saves | 1 at a time; per game exclusive with W jobs on that game and with the game running | `sync-saves` (directional, explicit), `download-saves` |
| **L** launch | unlimited, highest priority | `launch <app> --json --skip-version-check [--offline]`; never queued behind W; refused if the game (or its base game) has a running/queued W job |
| **R** read | in-process | direct JSON reads |

- **Auth gate**: one in-memory gate for any spawn that calls `login()`; released at the first post-login log line
  or exit or 45 s (L§1.8). Launch requests jump the gate's wait list. Warm `user.json` at startup with
  `list-installed --check-updates --json`.
- `Failed to acquire installed data lock` (exit 0) = busy → retry in 5 s, never a failure.
- Queue semantics: jobs are keyed by (AppName, Kind) for idempotency; a paused job blocks only its own game,
  others run; reorder / move-to-top / pause-all / resume-all; persisted (`state/jobs.json` v2) and crash-resumed.
- **While a game runs** (Settings.WhilePlaying, default Pause): Pause = stop the running W job (kill, resumable) and
  hold the queue until the last session ends; Throttle = effective mode Background. Launch itself never waits.
- `cleanup` only when every lane is idle and no `tmp/*.resume` exists.

## 4. Download modes and priority (missing in v0.1, generalized)

| Mode | Legendary tree | Workers | Notes |
|---|---|---|---|
| Full | normal CPU priority, normal IO, normal memory priority | adaptive up to the measured optimum | truly uncapped |
| Balanced (default) | downloader processes normal; **file-writer process** low IO priority + below-normal CPU; memory priority low | same network concurrency as Full (target ≥ 85–90 % of Full network throughput) | disk priority is what keeps the PC smooth |
| Background | whole tree idle/below-normal CPU, very-low IO, memory priority very low, EcoQoS | capped | |

Idle full speed: `IIdleSignal` (no input ≥ 3 min, no game running) → effective Full; any input → back. Speed limit:
Job Object net-rate control if it works unelevated, else worker throttling (decide by measurement). Changing the
effective mode of a running job applies live where Windows allows (priority, IO priority, net rate) and otherwise
restarts it with resume. Exact parameters come from `docs/download-perf.md`.

## 5. Honest phases (download card)

Verifying (local reads only: files/bytes checked, read speed, bad files) → Repairing (only if bad files: "12 files to
fix · 340 MB", network + disk) → Downloading (network figures + disk) → Installing (disk only: the write/patch tail
after the network is done) → Finalizing. `JobInfo.Phases` lists the planned phases so the UI can draw a stepper
(e.g. Update = Preparing, Downloading, Installing, Finalizing; Verify = Verifying, Repairing, Verifying is shown
as Verifying→Repairing→Finalizing with the second verify inside Finalizing). Percent is whole-job, monotonic.

## 6. Data layout and migration (`%LocalAppData%\GliderData\`)

The data root is `%LocalAppData%\GliderData` since schema 3. `%LocalAppData%\Glider` is Velopack's install root (packId
Glider), which uninstall deletes, so up to schema 2 an uninstall took Legendary's sign-in and `installed.json`, `state\`
(incl. the cloud-save ledger), `backups\` (the only copies of overwritten saves and EGL files), logs and the WebView2 profile
with it (review H6). The store files under `state\` keep `"schemaVersion": 2`:

| File | Content |
|---|---|
| `data-root.json` | `{schemaVersion: 3, movedFrom, movedAt, directories, pendingDeletes, finished}` — commit marker of the data-root move |
| `state\schema.json` | `{schemaVersion: 3, migratedFrom: "0.1"|null, migratedAt, history: [{from, to, at, note}]}` — written LAST (commit marker) |
| `state\settings.json` | `Settings` v2 |
| `state\games.json` | `{schemaVersion, games: {<app>: {install?: InstallRecord, favorite, hidden, playtimeSeconds, lastPlayedAt, settings: GameSettings, shortcuts}}}`; `InstallRecord` = v0.1 `GameRecord` + appName (EGL link, needsVerification) |
| `state\collections.json` | collections |
| `state\jobs.json` | v2: v0.1 shape + `appName`, `title`, `options` (components/dlc), queue order; reader accepts PascalCase *and* camelCase `step` |
| `state\onboarding.json` | `{schemaVersion, completed, step, skipped}` |
| `state\saves.json` | cloud-save ledger per app (last synced hashes/mtimes, for the 3-way conflict check) |
| `state\prereqs.json` | installed prerequisite ids |
| `cache\library.json`, `cache\art\<app>\…` | caches (safe to delete) |
| `backups\migration\v0.1-<ts>\` | byte copies of every v0.1 `state\*` and `cache\*.json` before migrating (a retry reuses the newest byte-identical one) |
| `backups\saves\<app>\<ts>\` | save backups before every overwrite |

**Migration v0.1 → v2** (`Infrastructure/Migrations`, runs before any store loads, idempotent, tested from a
realistic fixture of this machine's real v0.1 shapes, incl. the BOM files and the `+` escapes):
1. If `state\schema.json` has version ≥ 2: nothing to do.
2. Back up `state\*` and `cache\*.json` to `backups\migration\v0.1-<ts>\` (copy, verify sizes), or reuse the newest backup
   whose files match byte for byte (a failed start retried must not pile up copies, review L8).
3. `game.json` → `games.json["Fortnite"]` (install record, playtime, lastPlayedAt); v0.1 global `launchArgs` →
   Fortnite's `GameSettings.LaunchArgs`; v0.1 `autoUpdate: bool` → `Always|Never`; new settings get defaults
   (`DownloadMode = Balanced`); `defaultInstallBase` also seeds `libraryFolders`.
4. `jobs.json` v1 → v2 with `appName = "Fortnite"` (resume state kept; Legendary's `tmp\Fortnite.resume` untouched).
5. `onboarding.json`: completed if v0.1 completed **or** a game record existed; art/size caches → per-app caches.
6. Write new files atomically, then `schema.json`. v0.1 files are left in place (never deleted) so a downgrade or a
   failed run loses nothing; on any exception log it, keep v0.1 files, and retry next start.
`legendary\` (auth, installed.json, manifests, resume files) and `webview2\` are not touched.

**Schema 3: the data-root move** (`Infrastructure/Migrations/DataRootMover.cs`, called by the host through `DataRoot.Prepare`
right after it holds the single-instance mutex and before logging, the WebView2 environment or Core open anything; an explicit
`--data-dir` is used as it is and never moved):
1. `GliderData\data-root.json` committed → use it (finishing any post-commit step an interrupted run left). No data folder in
   the old root (or a `data-moved-to.txt` without a marker) → commit the new root without moving anything.
2. Otherwise move each of `webview2\`, `legendary\`, `overlay\`, `logs\`, `placeholder\`, `cache\`, `state\`, `backups\` that
   exists, in that order (the ones another process may hold open first). Same volume: `Directory.Move`, an atomic rename of the
   whole tree that Windows refuses while any file inside is open, so a directory is never half moved. Locked: retried for ~2 s
   (a WebView2 browser or orphan Legendary of the previous session exiting), then **every** directory is put back and the session
   runs on the old root; the move is retried next start. Another volume (ERROR_NOT_SAME_DEVICE, e.g. a junctioned folder): copy
   to `GliderData\.moving\<dir>` (sources opened denying writers, each file flushed to disk), verify file list and sizes (plus
   SHA-256 for `state\` and `backups\`), then rename into place; the source stays until after the commit. Velopack's own files
   (`current\`, `packages\`, `Update.exe`, `Glider.exe`, `.portable`…) are never touched.
3. Write `data-root.json` (the commit), then the post-commit steps, each idempotent and repeated until `finished`: re-point
   absolute paths into the old data folders (`legendary\overlay_install.json`, `state\jobs.json`) and the HKCU EOS overlay
   registration, write `data-moved-to.txt` in the old root, delete the copied sources.
4. Resume rule (no journal needed): before the commit a directory is in the new root only because the mover put it there
   complete, so *only in the new root* = moved, *in both* = verified copy awaiting its source delete, anything under `.moving\`
   = unfinished copy (discarded). If putting back fails too, the data is split: the host shows an error and exits without writing
   in either root, and the next start resumes forward. Tested by crashing after every step (same and cross volume).
5. Then Core's `Migrator` runs in the new root: v0.1 → schema 2 as above (so a v0.1 user is moved first, converted second; the
   conversion's backup lands in the new root, never in the folder uninstall deletes), then `schema.json` records schema 3 with
   the history kept (`migratedFrom` stays "0.1"). Moving first is the only order that works: the move must precede everything
   that opens the data root, and the conversion needs Core.
6. Velopack: updates are unaffected (`current\` is replaced, the data is elsewhere). The uninstall hook keeps the data; when
   this install never got to move it (never started, or deferred) and no Glider is running, it tries the move (renames only).
   A downgraded build would start fresh in the old root; once committed, the new root wins and the old folders are left alone.

## 7. Onboarding

Welcome → Sign in → Scan (every EGL `.item` on every drive + v0.1's Fortnite record + quick scan; selectable list
with art/title/version/drive/size, all selected; select all/none; "Locate another folder…"; import = one Import job
per game with per-game progress and outcome) → Library folders (free space per drive) → Download mode → Done (Home,
library populated). Steps persist via `onboarding.setStep`; re-runnable via `onboarding.restart`.

## 8. Ownership of Phase 2 work (to avoid merge conflicts)

Each feature agent owns its Core folder + its frontend feature folder; shared files (`Models.cs`, `IGliderRpc.cs`,
`GliderService.cs`, mock `backend.ts`, router) get additive changes only, and contract changes are regenerated with
`dotnet run --project tools/Glider.ContractGen`.
